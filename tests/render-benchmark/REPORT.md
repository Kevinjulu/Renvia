# Render fidelity investigation: report after Phase 3

Status: **investigation only. No production routing, pricing, credits or settings changed. BP is not production ready.**

Evidence: 7 cases (4 Lakeside/design-2 plus 3 new sources incl. a clean orthographic 2D elevation), 3 rounds, about 55 renders and 50 vision calls, roughly $3 of fal spend. Raw outputs are under `results/` (git-ignored); every run stores inputs, prompts, seeds, request ids, timings and errors in `run.json` / `run3.json`.

## 1. What each phase established

| Phase | Finding |
| --- | --- |
| Audit | Strict mode has had no technical enforcement since commit `0220c0e` (Canny route removed) while still billing 2 credits. FLUX 3 edit has no seed/strength/structure control. |
| Round 1 | The long Strict prompt keeps geometry well on Lakeside, but can suppress photorealism and finish transfer. A FLUX General img2img route from the sketch returns the sketch. |
| Round 2 | Hand-written inputs: Kontext + material spec + structure inventory (BP) was the most faithful and fastest; a short FLUX 3 prompt (AL) fixed realism but leaked reference roof/deck on the low-res sketch (BM-04). |
| Phase 3 | **Automatic** inputs work partially, with specific, measurable failure modes (below). |

## 2. Phase 3 results (all inputs generated by the vision modules)

Vision model for extraction and verification: `google/gemini-2.5-flash` via fal `openrouter/router/vision`. Seed 12345.

"Gate" = verifier says roof kept, camera kept, photorealistic, no added architectural element, and at least 80% of checklist items kept. The verifier is itself a model (see 4).

| Approach | Inputs | Gate passes | Mean checklist kept | Mean colour dE vs reference | Mean render time |
| --- | --- | --- | --- | --- | --- |
| **BA**: Kontext, auto inventory + auto materials | automatic | 2/7 | 0.77 | 10.3 | 13 s |
| **BA2**: BA + element locks, forbidden-feature list, colour anchors | automatic | **5/7** | 0.85 | 9.2 | 13 s |
| **AL**: FLUX 3 edit, short prompt, reference image attached | none needed | **5/7** | **0.93** | 9.4 | 25 s (30-95 s) |
| BP1: Kontext, **hand-written** inventory + spec (4 cases) | manual | 4/4 | 0.94 | 12.0 | 8-16 s |
| A: production Strict prompt (4 cases, Round 1) | none | 1/4 | 0.85 | 12.4 | 62-95 s |

Per case (P = gate pass): BM-01 BA F, BA2 P, AL P · BM-02 F, P, P · BM-03 F, F, F (hand BP1 P) · BM-04 F, P, **F** (AL leaks roof tiles) · BM-05 P, P, P · BM-06 P, P, P · BM-07 F, **F**, P.

Reading it honestly:

- **Not one approach dominates.** Failures barely overlap: AL fails BM-04 (low-res sketch, adverse hip-roof reference); BA2 fails BM-07 (camera shifted, stone cladding added from the reference) and BM-03. Best-of-two would pass 6/7, but only if the verifier picks correctly.
- **Automatic inputs lost to hand-written ones.** On the same four cases BA2 passed 3/4 where hand-written BP1 passed 4/4.
- **The core goal held in every case.** No approach imported reference architecture: no gable, pediment, columns or A-frame appeared in any BA/BA2 render. The residual failures are details and colour, not redesign.

## 3. Where automation breaks (extraction accuracy)

Checked against the drawings by eye. Gemini Flash output was **identical on repeat runs (temperature 0), which proves stability, not accuracy**.

| Source | Claimed | Actual | Effect |
| --- | --- | --- | --- |
| Lakeside fins | 15, confidence "high", both runs | **10** | An "exactly 15" instruction would make a renderer invent fins. Counts above 3 are now never passed on. |
| Lakeside upper-left opening | "door" | tall window | Mild; the renders kept a window. |
| BM-04 storeys | 3 | 2 | Did not harm the render. |
| BM-04 / BM-05 roof | "mixed" while describing "multiple flat roof sections" | flat | Composer asked for tiles until it was made to require both label and description. |
| Uncertainty reporting | 0 unknowns, 0 low-confidence items in all 7 cases | n/a | Confidence gating is useless with this model. |

A second model (Claude Sonnet 4.5) was better calibrated (3-5 explicit unknowns per drawing, declined to give a fin count) and disagreed with Gemini on BM-05 guardrails (7 rails vs 2) and on BM-01 roof. It cost $0.042-0.058 per elevation and took 40-50 s versus $0.0055 and 12 s. **Disagreement between two models is a usable uncertainty signal; a single cheap model's confidence is not.**

Composer bugs the benchmark exposed (all fixed in `compose.mjs`): forbidding "columns, balconies" when the source has them; recolouring a flat roof from a reference's red tiles; prompts of 3,000+ characters.

## 4. Fidelity verifier (P1 prerequisite)

Correct on the large failures: BM-04 AL/A roof changed (confirmed by eye), BM-03 Round-1 A not photoreal (confirmed), BM-07 BA camera changed (confirmed). Weak on small items: it reports tiny downpipes "missing" on dark renders and flags the glass guardrail "changed" in 17 of 28 renders. It also grades against the *auto* inventory, so inventory errors propagate. **It is a useful triage signal, not yet a release gate.** It needs a human-labelled calibration set before any retry or refund logic relies on it.

## 5. Two requested investigations

**Glass guardrail replaced by thin rails.** The explicit "stay clear frameless glass" lock produced no visible change in any case where it applied. A glass panel with a dark top rail is nearly indistinguishable from thin rails at render resolution, so this may be rendering reality as much as substitution. Treat as unsolved and low priority; do not promise it.

**White drifting to cream.** The neutral-light/"no cream" clause did **not** fix it: BM-02 and BM-05 BA/BA2 walls were still judged "light beige". The reference-image route (AL) kept "bright white" in BM-01, 02, 05 and 07. Colour carried by words was weaker than colour carried by pixels. Lighting copied from the reference (dusk in BM-01 and BM-06) also made renders dark and hard to verify.

## 6. Cost and latency of the full pipeline (measured)

| Step | Cost | Time | Frequency |
| --- | --- | --- | --- |
| Structure extraction (Flash) | $0.0055 | 12 s | once per elevation, cacheable |
| Material extraction (Flash) | ~$0.003 | 8 s | once per reference, shared by all four elevations |
| Kontext render | $0.040 | 13 s | per render |
| Verification (Flash) | $0.0034 | 15 s | per render |

First render of one elevation by the BA2 path is about $0.052 and about 40 s; later renders with a cached spec are about $0.043 and about 28 s. The comparable AL path is about $0.051 and about 40-110 s (FLUX 3 alone took 30-95 s). **The earlier "8x faster" applies to the render step only; the measured end-to-end advantage is about 1-2.5x, not 8x.** A second model for consensus extraction adds about $0.05 and about 45 s per elevation.

## 7. Recommendation

1. **Do not route Strict to BP, and do not claim geometry guarantees.** The evidence supports "source-faithful", not "guaranteed".
2. **Restore honesty first (no engine change needed):** relabel or reprice Strict, and update `docs/strict-source-fidelity.md`, which still describes a Canny route that no longer exists.
3. **Standard route: adopt the short prompt.** It is the only change with a clean positive result at no extra cost (on the four cases both ran, AL passed the gate 2/4 and production A 1/4; AL passes 5/7 on all seven), and it needs no new infrastructure.
4. **Strict route (proposal, not authorised): two candidates + verify.** Render an AL-style and a BA2-style candidate in parallel (about $0.09), verify both, return the better one that passes, otherwise retry once or refund. Failures barely overlap, so this beats either alone, and it makes the 2-credit price honest. Requires verifier calibration first.
5. **Lighting and landscape are user settings** (default neutral daylight), not taken from the reference.
6. **Carry white and colour via pixels, not words** (see next experiments).

## 8. Next experiments (before any migration)

1. **Calibration set:** 30+ human-labelled renders to measure verifier precision/recall. Gate for everything below.
2. **Swatch-board second image:** build a shape-free image from the reference (solid measured colour chips plus texture crops) and pass it to a multi-image Kontext endpoint. Targets the white-to-cream gap without leaking reference shape.
3. **Consensus extraction:** two models; pass only elements and counts both agree on; list disagreements as "unknown" and surface them for user edit.
4. **Larger corpus:** at least 15 sources, including real flat 2D CAD elevations, different building types, and low-resolution inputs.
5. **Multi-seed variance** for BA2 and AL on every case (round 2 had three seeds on four cases only).

## 9. Proposed project-level design specification (design only, not integrated)

```ts
interface ProjectDesignSpec {
  version: 1;
  /** Provenance, so a user can see where each value came from. */
  source: { referenceIds: string[]; extractedAt: string; model: string; promptVersion: string };
  surfaces: Array<{
    surface: "walls_primary" | "walls_secondary" | "cladding" | "base_plinth" | "roof_covering" | "window_frames" | "doors" | "soffit_fascia" | "guardrail" | "paving";
    material: string;
    colour: { name: string; hex: string | null };
    finish: string | null;
    origin: "extracted" | "user";      // user edits always win and survive re-extraction
    confidence: "high" | "medium" | "low";
  }>;
  lighting: { mode: "neutral_day" | "match_reference" | "custom"; note?: string };   // default neutral_day
  landscape: { enabled: boolean; groundCover?: string; planting?: string; hardscape?: string };
  forbiddenFeatures: string[];          // from the reference minus anything the source has
  perElevationOverrides?: Partial<Record<"front" | "right" | "back" | "left", Partial<ProjectDesignSpec["surfaces"]>>>;
}
```

Rules: one spec per project, read by all four render jobs; each elevation keeps its **own** structure analysis (geometry never shared); the spec is shown as editable chips; changing a surface invalidates only renders that depended on it.

## 10. Migration plan with acceptance criteria

| Step | Scope | Acceptance criteria |
| --- | --- | --- |
| M0 | Honesty: relabel/reprice Strict, update docs | Strict copy and credit price match what the route actually does; no "Canny" claim remains. |
| M1 | Standard route: short prompt | On the 7 benchmark cases plus new corpus: gate pass rate >= current production; no case worse than production on photorealism. Reviewed by a human on all cases. |
| M2 | Verifier calibration | On >= 30 human-labelled renders: roof/camera/added-element detection recall >= 0.9 and false-alarm rate <= 0.15; small-element checks excluded or down-weighted. |
| M3 | Extraction hardening | Counts above 3 never reach the renderer; consensus or user confirmation for any element used as a hard constraint; on the corpus, no fabricated element in the constraint list. |
| M4 | Shared project spec + edit UI | Four elevations of one project produce the same wall/frame/roof colours within dE <= 6 unless overridden; user override persists across re-extraction. |
| M5 | Strict route (two candidates + verify) | Behind a flag. >= 90% of delivered renders pass the verifier gate on the corpus; every attempt stored; credits reserved and refunded exactly; cost per delivered render within the quoted credit price. |
| M6 | Release gate | A regression run of this benchmark on every model, prompt or control-strength change; do not ship a change that lowers the gate pass rate. |

Edit-tab behaviour is unaffected by all of the above. Edits keep their own route and their masked-composite guarantee.

## 11. Limits of this evidence

- Seven cases, one seed per approach, three Lakeside cases share a single source.
- The verifier is a model and was only spot-checked by eye.
- Colour dE is computed on dominant clusters and is only a rough signal.
- fal does not return billed cost; render costs are registry estimates and should be reconciled against the fal dashboard.
- Specs for Round 2 were hand-written; Phase 3 inputs are automatic. The two are not perfectly comparable (the hand-written inventory also described each element differently).
